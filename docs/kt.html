Job Tracker

A personal job-application tracker. Each user keeps their own board of applications (Saved, Applied, Interview, Offer, Rejected), adds notes, schedules interviews, pastes a job posting to have AI pre-fill the form, and asks an AI assistant questions about their own data.

What a user can do

  • Sign up, log in, log out (cookie session, 7 days).
  • Add an application: company, role, link, location, salary, skills, interview time.
  • Extract (AI): paste a posting, Groq pre-fills the fields.
  • Move it between stages with the status select; Edit any field on the card.
  • Keep notes per application.
  • Ask about your applications: a streaming chat that can search applications and list upcoming interviews.

Tech stack

Next.js 16React 19TypeScriptTailwindDrizzle ORMNeon PostgresZod 4bcryptjsGroq (gpt-oss-120b)VitestPlaywrightGitHub ActionsVercel

Next.js 16 is not the Next you may know. It uses Cache Components (anything that reads cookies or the clock must sit inside <Suspense>) and proxy.ts (the old middleware.ts). Read node_modules/next/dist/docs/ before changing framework-level code (see AGENTS.md).

The five ideas to remember

IdeaWhat it means in this codebase
1. The server owns identityuserId always comes from the session cookie, never from a request body, URL or the AI model. Every query filters by it.
2. Validate at the edgeEvery API body goes through a Zod schema in lib/validation.ts before anything else touches it. Pure files, easy to unit test.
3. Never leakNot yours / not found → the same 404. Failures → generic messages. Logs never contain passwords, tokens, cookies or user text (lib/log.ts).
4. The AI is a guestModel output is validated (extraction), tool results are data not instructions, the model can only call two read-only tools bound to the current user.
5. Everything testable runs without the networkModel, DB and clock are injected or isolated. Unit tests (Vitest) plus one real-browser e2e (Playwright) on an isolated database.

    Data model

    Four tables in Neon Postgres, defined in db/schema.ts. Deleting a user cascades to everything they own. Click a table to see how it is used.

    Migrations

    Drizzle generates SQL into drizzle/000N_*.sql (npx drizzle-kit generate). Apply with npx drizzle-kit migrate against the target database. Production, the e2e branch and any test branch are separate Neon branches: migrate each one you use.

    Drizzle decides which migrations to run by comparing the journal's when timestamp. A migration whose timestamp is older than the last applied one is silently skipped. If a migration "ran" but the column is missing, check drizzle/meta/_journal.json.

    Live demos

    These are small re-implementations of the real rules, running in your browser. They are meant to build intuition; the real code and its tests are named under each demo.

    A. API explorer: who answers, and with what?

    Pick who is calling and which route. The result shows which layer answered. Ana owns application 5 (with note 9); Bala owns application 6. Real tests: scripts/security-check.ts (checks 1-2).

    B. PATCH validator: absent vs null, strict, ranges

    Edit the JSON body of PATCH /api/applications/5. Rules from updateApplicationSchema in lib/validation.ts. A missing key means "leave it alone"; null means "clear it".

    C. Time zones: the datetime-local trap

    <input type="datetime-local"> gives a value with no time zone (2026-11-24T15:00). The API needs an absolute instant. We convert with the browser's zone on the way out and back on the way in (lib/datetime-local.ts). Pick a zone to simulate; the demo does the same maths with Intl.

    D. Chat stream: what the browser actually receives

    POST /api/chat answers with NDJSON: one JSON event per line, flushed as it happens. The UI is a reducer over those events (lib/chat-client.ts). Real code: lib/chat.ts (loop), lib/chat-stream.ts (stream), lib/groq-stream.ts (model).

    CI (GitHub Actions)

    Two jobs on every PR and push to main:

    • ci: npm ci → typecheck → lint → test → build (dummy DATABASE_URL).
    • e2e: installs Chromium, runs Playwright against a built app and the isolated Neon e2e branch (secret E2E_DATABASE_URL); uploads playwright-report/ on failure.

    Dependabot opens weekly update PRs.

    E2E safety: it can never touch real data

    • playwright.config.ts calls requireE2eDatabaseUrl() first: it throws if E2E_DATABASE_URL is missing, invalid, or points at the same Neon endpoint as DATABASE_URL (pooled and direct hosts are compared after stripping -pooler).
    • The test server is started with DATABASE_URL = E2E_DATABASE_URL and a dummy Groq key; the chat is mocked at the network.
    • Teardown deletes users matching e2e+%. The guard itself has unit tests (tests/e2e-guard.test.ts).

    Observability

    • Structured logs: one JSON object per line from lib/log.ts (Vercel → Logs can filter by field). Keys that look sensitive (password, token, cookie, hash, database_url…) are redacted automatically; the rule is still "never pass them in".
    • Chat and extraction log counts only (text length, steps, tool calls), never the question, answer or posting text.
    • Unexpected errors become a generic 500 {"error":"Internal server error"} to the client; the detail stays in the log (lib/api-error.ts).

    Gotchas & design decisions

    The "why" behind choices that look odd at first. Click a row to expand.

    Known gaps (be honest in a review)

    • No rate limiting on login, /api/chat or /api/extract. A correct limit needs shared state (Redis); deferred. Risk accepted for a small friend group.
    • CSP allows inline scripts/styles (Next's bootstrap); a nonce-based CSP would disable prerendering.
    • Sessions are not rotated on login; no "log out everywhere".
    • The card shows the interview in IST while the edit input uses the browser's zone: identical for IST users, different elsewhere.
    • Chat on Groq's free tier is limited to ~8,000 tokens per minute: a busy minute returns the friendly 503 / "AI is busy" message.
